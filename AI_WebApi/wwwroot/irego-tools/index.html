六项工具，一条可信调用链

当前开放患者上下文、既往记录分页查询、单次会话分析、单次报告图片、跨报告分析与跨报告图片六项工具。 六者统一读取 project，身份参数由 Dify 系统/运行时绑定； LLM 只能选择前一工具真实返回的 session_ref，不能填写患者 ID 或编造会话引用。旧 ID、v1 会话引用、旧缓存及旧报告链接已停用，不再可用；请重新绑定患者、查询记录并生成报告。

01 · Authentication boundary

认证不是一个字段，而是三次检查

工具服务不会因为请求里写了一个患者编号就相信它。调用来源、身份绑定和数据库归属必须逐层成立。

1

Dify 服务认证

凭据 Dify 凭据库自动发送 Authorization: Bearer …，服务端进行恒定时间比较。

2

系统身份上下文

系统填写 system_context 由已登录入口或运行时变量绑定，禁止让模型猜测。

3

数据库用户查询

服务端规则 将 system_context.user 解析为 dbuser.Id，患者与机构信息全部从数据库取得。

患者登录业务系统确认当前人是谁，并建立患者与机构绑定。
Dify 接收上下文入口把绑定结果放入受控变量，不写入自然语言提示词。
工具自动组装服务 Token 与 system_context 由工具配置填入。
IREGO 再校验验证 Token，并将 user 解析为正整数数据库用户 ID。
返回脱敏数据只返回患者引用与会话引用，不开放任意 SQL 或表字段。
关键边界： HTTP 服务只能看到最终请求，无法识别某个 JSON 字段到底是 Dify 系统填的还是 LLM 填的。 因此必须在 Dify 中把系统字段锁定为预设/运行时绑定，并确保服务 Token 永不进入模型上下文。
02 · Interface specifications

接口与参数意义

六项工具接口均为 POST、只读、JSON。Bearer Token 是工具凭据；请求体同时包含系统参数与业务参数。

字段来源意义
system_context系统与前两项工具相同，由 Dify 自动绑定患者用户。
session_ref工具结果只能选择上下文工具返回过的引用。后端重新校验当前患者归属与完整完成状态。

/api/ai/patients/tools/get_irego_longitudinal_analysis
跨报告查询

请求示例

{
  "system_context": {
    "user": "7",
    "conversation_id": "conv-42"
  },
  "selector": "latest_contiguous",
  "report_count": 4,
  "session_refs": [],
  "project_scope": "all",
  "detail_level": "standard",
  "quality_detail": "summary"
}

业务参数

参数可选值意义
system_context系统与其他工具相同，由 Dify 自动绑定患者用户；请求不提供 patient_id。
selectorlatest_contiguous / session_refs取最近连续窗口，或使用已返回的引用确定窗口两端。
report_count2—12latest_contiguous 模式下需要截取的连续报告位置数。
session_refs2—12 个稳定引用只允许选择前序工具返回值。后端自动纳入最早与最晚引用之间的所有报告位置，包括中间不完整报告。
project_scopeall / walking / sit_stand / games / balance限制返回的训练项目范围，不允许跨项目合并。
detail_levelsummary / standardstandard 在每个分段中同时返回数据库指标事实；图表序列两种级别都会返回。
quality_detailnone / summary / full控制质量问题细节，不改变窗口选择或比较结果。

主要出参

字段结构意义
window对象请求数、实际纳入数、完整/不完整报告数、起止时间和 before_after / trend / descriptive_only 模式。
reports[]报告位置数组保留连续位置、匿名 session_ref、日期、完整性和完成率；不完整报告隐藏 session_ref 和指标，但保留灰色位置与日期。
projects[]同项目数组按严格项目身份分组。游戏必须 GameMode 相同，平衡项目必须 BalanceMode 相同；未知身份不进入跨报告比较。
lanes[]重复分段轨道计划分段先定轨道；配置完全相同优先匹配，重复相同配置再按计划原顺序匹配，不取最佳值或平均值。
segments[]各报告分段present、segment_missing 或 report_incomplete；缺失位置没有伪造值。
metric_series[]逐指标序列包含 metric_code、名称、单位状态、comparison_eligible、chart_eligible 和限制原因。
points[]图表点数组保留报告日期位置、原值、标准值、游戏难度和比较条件；可见有效点统一以实线连接，缺失报告位置仍保留为空位。
capability_evaluations[]分能力评价返回 improved / stable / worsened / mixed、证据指标、阈值强度、规则版本，以及 basic_evaluation、extended_explanation、life_hint 三层患者文案。patient_message 与基础评价保持兼容。
quality / sources边界与来源说明趋势资格、可见限制和 robotdb_main 事实来源，不返回数据库主键。
能回答： 最近 N 个连续报告位置的完整性；同一训练项目、同一分段的原始指标变化；同一游戏的同难度单位时间得分趋势和跨难度任务表现； 缺失报告日期位置；分运动能力的改善、无明显变化、表现下降或有好有坏；每份完整报告按计划—报告分段匹配计算的完成率。
不能回答： 不同项目之间的优劣、缺失值估算、数据库没有的指标、跨游戏综合排名，以及“已经康复、治疗有效”等临床结论。

03 · Response structure

统一信封与核心结构

所有业务结果使用相同信封。只有认证、请求格式、越权和依赖故障使用非 200 HTTP 状态。

success

主体结果完整，且没有需要提示的数据质量问题。

partial

仍返回可用数据，同时用 reason_codes 说明降级或质量提示。

unavailable

HTTP 200，但没有结构有效的 IREGO 会话，例如仅有计划或报告 JSON 无效。

稳定会话引用： session_ref 使用带版本前缀的 HMAC-SHA256 签名， 格式为 irego_s_v2_<128-bit-signature>。 签名输入绑定租户、患者、计划、报告和报告结构，但输出不暴露这些数据库主键。 查询指定引用时，服务会针对当前患者的可用会话重新计算并匹配；进程内缓存只用于性能优化。 部署时必须通过 IReGoTools__SessionRefSigningKey 提供至少 32 字节的持久随机密钥； 容器重建必须继续使用同一密钥，真实值不得进入 Git、日志或提示词。
04 · Report record blocks

ReportList 元素是报告记录分段，不是独立项目

report_item_count 为兼容字段，含义统一为“报告记录分段数”； 新增 report_block_count 与 report_block_label 明确表达。

sequence

保持 ReportList 原始顺序，从 1 开始，不按类型重新排序。

display_name

后端提供“步行训练第N段”等可读名称；游戏优先使用真实 GameName 或 GameMode。

调用方表述

三条 walking 记录应说“3段步行训练记录”，不得说成三个不同训练项目。

{
  "overview": {
    "report_item_count": 3,
    "report_block_count": 3,
    "report_block_label": "报告记录分段数",
    "total_training_duration": 263,
    "duration_unit": "s",
    "total_training_duration_display": "263秒（约4分23秒）"
  },
  "report_blocks": [
    { "sequence": 1, "rehab_content": "walking", "display_name": "步行训练第1段" },
    { "sequence": 2, "rehab_content": "walking", "display_name": "步行训练第2段" },
    { "sequence": 3, "rehab_content": "walking", "display_name": "步行训练第3段" }

名称边界： 当源数据没有具体名称时，必须使用后端生成的可读分段名；不得根据指标或上下文编造具体项目名称。
05 · Duration unit evidence

确认单位直接写入原有 unit

不新增 display_value、display_unit 或 display_text。confirmed 单位可直接用于患者朗读；provisional_usable 只限本次记录描述。

源字段含义单位状态与证据
WTrainingWalktime 步行训练时长 s confirmed。业务方已确认；患者 461 最新报告为 41、180、42，合计 263 秒，计划创建到结束约 748 秒。数据库交叉样本中，367 份含步行时长的报告共 440 段；138 份具有可比较时间窗，均可按秒解释，其中 42 份只有按秒才与时间窗一致。相关 IREGO 协议中的训练时长字段也以秒表达，但未把它作为该字段的唯一证据。
STrainingSitTime坐站训练时长空unverified，不得猜测。
GTrainingTime / GTime游戏训练/设定时间空unverified，当前报告图片展示原值但不附单位。
RTrainingBalanceTime / BTime平衡训练/设定记录时间空unverified，当前报告图片展示原值但不附单位。
WAvgGaitPeriod / WAvgStep平均步态周期 / 平均步幅s / mprovisional_usable，只限单次记录描述。
沿用旧指标结构： 指标继续返回 metric_code / raw_value / normalized_value / unit / unit_status 等字段。 既有 total_training_duration_display 仅保留在会话总时长摘要中，不扩展成通用展示字段。
06 · Deterministic rules

当前数据库的直接判定规则

实现只依赖当前配置的数据连接。切换连接后不需要开启对账开关或修改生产白名单。

唯一事实源

只查 project

患者身份统一使用 project.dbuser.Id。旧 ID 不再映射，旧会话引用、缓存和报告链接已停用，请重新查询或生成。

结构准入

主链引用闭环

rehabplan.devicetype=1、templates.modelid=1、患者 UserType=2、医生 UserType=1，且患者、医生属于同一存在的 Vendor 记录；任一关键引用缺失即排除计划。

汇总报告

report.id 对应计划 id

robotdb.report.id=robotdb.rehabplan.id，物理上一份计划至多一份汇总报告。孤儿报告直接忽略，不尝试跨库补齐。

原始数据

只作执行证据

reportdata 与 reportdata_new 的多行记录不是多份汇总报告；本期不解析正文，仅用于识别“完成标志与执行证据冲突”。

完成状态

CompleteStatus 分层

1 为完整完成；0 且有报告或非空原始数据为 execution_unknown；其余按预约日是否结束分为未开始或未完成。当前数据不能证明“意外中断”。

报告可用

完成且结构有效

只有状态为 completed，且 JSON 可解析并包含 ReportList，才进入会话分析与单次报告图片。

时间语义

不伪造开始或结束

StartTime 映射为预约时间；createtime 是来源记录创建时间；reporttime 是报告记录时间。报告时间早于计划记录创建时间时，不参与“最近一次”选择。

数值安全

保留原值，剔除非有限数

NaN、Infinity 不进入聚合；距离大于 0 而步数和平均速度同时为 0 时，只提示指标可能不完整，不判定正常。

07 · Database switch readiness

统一新患者 ID，连接切到 project

三个工具共用同一套 robotdb_main Repository；“multisource”只为兼容工具名，不再表示跨数据库合并。

  • 跨库对账、补齐、隔离和切换门控
  • wx_*、备份表与临时表参与患者结果
  • 把 raw data 多行误认为多份汇总报告

  • 患者、医生、机构、模板、计划和报告在同一命名空间闭环
  • 完成状态与报告结构同时决定会话是否可用
