System-filled context ≠ model parameters

“Dify 自动填写”能解决什么，不能证明什么？

它能防止 LLM 猜错或篡改身份参数，是实现验证的必要条件之一；但它并不会自动证明屏幕前的人就是该患者。 真正可信需要上游登录绑定、Dify 工具服务凭据和 IREGO 数据归属校验共同完成。

结论
论断有条件成立，不能简化成“自动填了就可信”

Dify 官方明确支持预设参数，并在工具调用时把运行时参数与模型产生的参数合并。 因此“身份参数不交给 LLM”是可实现的。工程上仍要锁定参数来源，并对调用服务和患者归属分别验证。

01 · Two different questions

先分清“谁在调用”和“要查谁”

本项目只需要一个 Dify 系统用户 ID，但仍要分别验证调用服务和用户编号来源。

服务认证

谁在调用 IREGO API？

由 Dify 凭据库发送的 Bearer Token 回答。它只能证明“请求来自被授权的 Dify 工具”，不能单独证明患者身份。

身份绑定

这个 Dify 用户可以查哪个患者？

由 Dify 自动填写 system_context.user 回答。该值就是 dbuser.Id，IREGO 用它直接查询数据库。

本项目明确约定：Dify 的 user 就是数据库用户 ID。 因此不再传入 end_user_id、patient_id、business_id、tenant_ref 或 role。 但 user 必须由 Dify 系统自动填写，不能让 LLM 或浏览器自由指定。

03 · Parameter ownership

哪些参数由谁填写

参数所有权必须在 Dify 配置中固定。接口文档展示字段，并不代表允许模型生成它们。

参数组填写者LLM 可见/可改验证方式
Authorization: Bearer …Dify 工具凭据库不可见、不可改IREGO 与服务端配置的 Token 做恒定时间比较
system_context.userDify 自动填写不可改必填；大于 0 的十进制 dbuser.Id
conversation_idDify 运行时不可改只做追踪，不当作患者身份证明
selector、detail_levelLLM 或工作流可选择枚举白名单
session_ref上一步工具输出可引用，不可构造数据库 ID短期缓存绑定到当前患者上下文
04 · Concrete examples

三个例子看懂边界

✓
正确

小王登录后问“我最近练得怎么样？”

小王对应数据库用户 7。Dify 系统自动填入 user="7" 和服务 Token； LLM 只选择 latest_usable。IREGO 用 dbuser.Id=7 查询患者及其机构信息。

×
错误

用户在聊天里说“我是患者 99”

即便 LLM 很确信，也不能把 99 写进 system_context。自然语言不是身份凭证。 若请求缺少 Dify 服务 Token，直接返回 401；聊天里的“99”不会改变系统填写的 user="7"。

!
仍不充分

Dify 自动填了 user，但上游允许客户端随便指定它

自动填写机制本身工作正常，可是可信起点不存在。攻击者可以换一个 user 值冒充别人。 必须由已认证后端生成或映射 user，而不是直接信任浏览器传入值。

05 · Request example

系统组装后的请求

下面是到达 IREGO API 的最终 HTTP 形态。占位值来自 Dify 绑定配置，不要求模型输出这段 JSON。

POST /api/ai/patients/tools/
get_irego_session_analysis
Authorization: Bearer <DIFY_TOOL_SECRET>
Content-Type: application/json

{
  "system_context": {
    "user": "7",
    "conversation_id": "conv-42"
  },
  "selector": "latest_usable",
  "detail_level": "standard",
  "quality_detail": "summary"
}

服务端检查顺序

服务 Token 是否已配置且匹配未配置返回 503；缺失或错误返回 401。
system_context 是否完整合法缺失、ID 非正数、主体为空等返回 401。
user 是否为有效数据库 ID非数字、0 或负数返回 DIFY_USER_ID_INVALID。
数据库用户是否存在按 dbuser.Id 查询；不存在或已删除返回 404。
业务参数是否在枚举范围非法 selector/detail_level 等返回 400。
06 · Dify configuration checklist

落地配置清单

在服务端设置密钥使用环境变量 IReGoTools__DifyServiceBearerToken，不要把真实值提交到 appsettings 或仓库。
在 Dify 工具凭据中设置同一 Token通过 Bearer 认证头自动发送，Token 不得出现在提示词、普通变量或日志正文中。
把 system_context 字段设为预设/运行时参数Tool Plugin 使用 form 类型；API Tool/Workflow 则绑定到受控入口变量。不要使用 LLM 推断模式。
建立 end_user 到患者的可信绑定推荐由业务后端在登录成功后传递，或在服务端维护映射，不接受聊天文本中的患者编号。
做三项鉴权测试无 Token、错 Token、非数字 user 都必须被拒绝；再测试模型尝试覆盖 user 时系统绑定值保持不变。
07 · Frequently asked

常见疑问

系统自动填参是不是就不需要 Bearer Token？

不是。自动填参解决“参数由谁产生”，Bearer Token 解决“请求来自哪个服务”。缺少后者，外部调用者也能自行构造同样的 JSON。

Dify 的 user 能直接查询患者数据库吗？

可以。本项目已明确约定 system_context.user=dbuser.Id，服务端将它解析为正整数后直接查询患者记录，并从数据库读取 BusinessId 等信息。

为什么 system_context 仍然出现在 OpenAPI 请求体？

因为 IREGO API 需要接收这些值，Dify 也需要知道字段结构。安全性来自 Dify 对这些字段的“系统/预设绑定”，不是来自把字段藏起来。

当前实现是完整的患者单点登录吗？

不是。当前实现完成了 Dify 服务认证、系统上下文校验和数据库租户复核。真实患者登录仍由上游业务系统负责；后续也可升级为签名身份令牌。

Official evidence

Dify 官方依据

  • Tool Plugin：Agent 中 llm 表示模型推断参数，form 表示可预设参数。
  • Agent Strategy Plugin：工具调用会合并运行时参数与模型产生的调用参数。
  • Dify API Reference：user 被定义为用户标识；API Key 应保存在服务端并通过 Bearer Header 发送。
本页解释当前 IREGO 接口实现的信任边界。详细字段见 接口规格主页。
